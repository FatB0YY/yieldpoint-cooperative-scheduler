# yieldpoint-cooperative-scheduler

Кооперативная многозадачность в TypeScript, написанная с нуля. Задачи-генераторы сами расставляют точки уступки, а сменный round-robin планировщик решает, когда их действительно прервать, укладывая все задачи в один общий бюджет времени. Результат работы задачи — промис, который вдобавок можно итерировать и слушать как поток событий.

Без зависимостей, около 600 строк, пять запускаемых демо. Репозиторий учебный: это та же механика, что стоит за планировщиком React и за `scheduler.yield()`, только собранная в объёме, который целиком помещается в голову.

## Проблема

JavaScript выполняет код в одном потоке. Пока работает синхронная функция, движок больше не делает ничего: не рисует кадр, не обрабатывает клик, не принимает соединение, не запускает колбэк таймера. Event loop проворачивается между задачами, но не внутри одной задачи.

```js
function bigArray(n) {
  const array = [];
  for (let i = 0; i < n; i++) array.push(i);
  return array;
}

for (let i = 0; i < 20; i++) {
  console.log(bigArray(1_000_000).length);
}
```

Запустите `node demo-problem.ts` и посмотрите на heartbeat. Таймер стоит на 10 мс и печатает не факт срабатывания, а реальный промежуток между тиками:

```
heartbeat +10ms
heartbeat +10ms
--- начали считать ---
chunk: 1000000
...
heartbeat +2841ms
```

Почти три секунды тишины. В браузере это около 170 потерянных кадров, на сервере — 170 запросов, застрявших в очереди на приём.

Хуже всего то, что эффект накопительный. Один обработчик на 30 мс незаметен. Но сотня таких, пришедших одновременно, выстраивается в очередь, и последний запрос ждёт три секунды, чтобы обслужиться за те же 30 мс. При этом p99 уезжает задолго до того, как сдвинется среднее, — по графикам средних такое просто не видно.

Стоит сразу проговорить, что именно мы чиним. Не объём вычислений, а длину самого длинного непрерывного блока. Работы меньше не станет — она станет нарезанной.

## Идея

Кооперативная многозадачность означает, что задача сама решает, когда уступить. Заставить её нельзя. Это прямая противоположность вытесняющей модели, по которой живёт операционная система: там планировщик отбирает процессор по прерыванию таймера и мнением задачи не интересуется.

Модель старая — так работали Windows 3.x и Mac OS 9 — и на уровне ОС от неё отказались не зря: одна зависшая программа вешала всю машину. Зато она вернулась внутрь процессов, где обходится дёшево и не порождает гонок. Каждый `await` в JavaScript — это кооперативная точка уступки. Горутины в Go, корутины в Kotlin и рабочий цикл React Fiber устроены точно так же.

Механизм дают генераторы. Генератор помнит, где остановился и что лежало в локальных переменных, поэтому обычный цикл можно приостанавливать и возобновлять, не выворачивая его наизнанку в конечный автомат:

```ts
function* work(t: TaskHelper, n: number) {
  let data: number[] = [];

  for (let i = 0; i < n; i++) {
    data.push(i);

    if (t.shouldPause()) {
      yield data;   // здесь приостановились
      data = [];    // сюда вернулись
    }
  }

  return "done";
}
```

Здесь чаще всего и возникает путаница: **`yield` сам по себе поток не отдаёт**. Он синхронно, в том же тике, возвращает управление тому, кто вызвал `.next()`. Если крутить генератор обычным `while`, поток окажется занят ровно так же, как раньше, только вдобавок появятся накладные расходы на сам генератор.

До event loop управление доходит лишь потому, что раннер планирует следующий `.next()` через макрозадачу. Отсюда и разделение ролей:

| Кто | Что решает |
|---|---|
| Генератор | Где его *можно* прервать |
| Планировщик | Где его *действительно* прервут и насколько |

На этом разделении держится вся библиотека.

## Использование

```ts
import { RoundRobinScheduler } from "./scheduler.ts";
import { taskBuilder, SimpleTaskHelper } from "./task.ts";

const scheduler = new RoundRobinScheduler({ quota: 8, delay: 4 });
const task = taskBuilder(scheduler)(SimpleTaskHelper);

const exec = task(function* doSomething(t, n: number) {
  let data: number[] = [];

  for (let i = 0; i < n; i++) {
    data.push(i);

    if (t.shouldPause()) {
      yield data;
      data = [];
    }
  }

  if (data.length > 0) yield data;

  return "done";
});

const run = exec(2_000_000);
```

Создание таски каррировано в три уровня: настраиваете один раз, вызываете сколько угодно.

```
taskBuilder(scheduler)   // 1. какой планировщик  ─┐ один раз
           (Helper)      // 2. какой хелпер       ─┘ на приложение
           (generator)   // 3. какая функция      ─── на каждую задачу
```

Первым аргументом в генератор всегда приезжает хелпер — его подставляет библиотека. Ваши собственные аргументы начинаются со второго, и возвращённая функция принимает только их.

### Три способа получить результат

`exec()` возвращает один объект, который одновременно удовлетворяет трём интерфейсам. Пользуйтесь тем, что удобнее в конкретном месте.

```ts
const run = exec(2_000_000);

run.on("data", (r) => {
  if (!r.done) console.log("чанк", r.value.length);
});

for await (const chunk of run) {
  console.log("чанк", chunk.length);
}

const result = await run; // "done"
```

События срабатывают синхронно, прямо внутри занятого блока. Асинхронная итерация просыпается на микрозадачах, то есть уже после того, как блок закончился. Поэтому в выводе Вы увидите сначала пачку строк `on(data)`, а следом ту же пачку `for await`. Так и должно быть, это не баг.

Цепочка переживает `.then`, `.catch` и `.finally`, поэтому такое тоже работает:

```ts
for await (const chunk of exec(n).catch(console.error)) { ... }
```

### `event-emitter.ts`

Раздаёт два события, `data` и `error`, и заодно работает как асинхронный итерируемый объект. Оба интерфейса живут на одном объекте одновременно.

Самое интересное здесь — буфер. Планировщик успевает прокрутить несколько шагов задачи внутри одного синхронного блока и несколько раз вызвать `emit()`, а потребитель асинхронной итерации просыпается только на микрозадаче, то есть уже после конца блока. Наивная реализация с ленивой подпиской внутри `next()` из-за этого теряет все чанки, кроме первого. Эмиттер держит буфер непрочитанных значений и FIFO-очередь ожидающих резолверов, поэтому ничего не пропадает, а два параллельных `next()` получают разные значения.

Экспортирует `EventEmitter`, `TEvent`, `TDataResult`, `TErrorResult`, `TDataHandler`, `TErrorHandler`.

### `scheduler.ts`

Решает, какая задача считается сейчас, сколько всего можно занимать поток и когда уходить в сон. Алгоритм — round robin: каждая задача получает один шаг и уезжает в конец очереди.

Планировщик здесь — стратегия. Реализуйте `IScheduler` по-своему (например, очередь с приоритетами наподобие lanes в React) и передайте в `taskBuilder` — остального трогать не придётся.

Интерфейс называется `IScheduler`, а не `Scheduler`, потому что имя `Scheduler` уже занято в DOM lib (Prioritized Task Scheduling API). Назовёте так же — и TypeScript начнёт требовать реализацию чужих `postTask` и `yield`.

Экспортирует `RoundRobinScheduler`, `IScheduler`, `ISchedulerOptions`, `IJobResult`, `TaskCancelledError`.

### `task.ts`

Оборачивает генератор, регистрирует его в планировщике и связывает каждый шаг с промисом и эмиттером.

Здесь же живёт `TaskHelper` — вторая стратегия библиотеки. Хелпер решает, когда генератору стоит предложить паузу. `SimpleTaskHelper` делает это по часам, но никто не мешает написать свой: смотрящий на `navigator.scheduling.isInputPending()`, с адаптивным порогом или с учётом приоритетов.

Экспортирует `taskBuilder`, `SimpleTaskHelper`, `TaskHelper`, `TaskHelperConstructor`, `TaskBuilder`, `EventablePromise`.

## API

### `new RoundRobinScheduler({ quota, delay })`

| Опция | Смысл |
|---|---|
| `quota` | Сколько миллисекунд можно занимать поток за один такт, причём на все задачи разом, а не на каждую. По сути это максимальная задержка, которую планировщик навязывает всему остальному в потоке. |
| `delay` | Сколько миллисекунд спать между тактами. Отвечает за долю процессорного времени, а не за отзывчивость. |

| Член | Описание |
|---|---|
| `quota`, `delay` | Геттеры, только чтение |
| `isRunning()` | Крутится ли цикл прямо сейчас |
| `push(job, handler)` | Зарегистрировать итератор. `handler` вызывается с результатом каждого шага, возвращается длина очереди |
| `run()` | Запустить цикл. Идемпотентен, `push` вызывает его сам |
| `clear()` | Отменить всё: закрыть генераторы, сеттлить промисы, снять отложенный таймер |

### `taskBuilder(scheduler)(Helper)(generator)`

Возвращает функцию, которая принимает аргументы Вашего генератора без ведущего хелпера и отдаёт `EventablePromise`.

### `EventablePromise`

| Член | Описание |
|---|---|
| `await` | Значение из `return` генератора |
| `.on("data", h)` | Каждый шаг в виде `{ done, value }`. Возвращает себя, поэтому вызовы можно чейнить |
| `.on("error", h)` | `{ done: true, error, value: undefined }`. Тоже возвращает себя |
| `.off(event?, handler?)` | Снять один обработчик, все обработчики одного события или вообще всё |
| `for await` | Отдаёт промежуточные значения и завершается на финальном шаге |
| `.then` / `.catch` / `.finally` | Ведут себя как обычно, результат остаётся eventable |

### `TaskHelper`

```ts
interface TaskHelper {
  shouldPause(): boolean;
}
```

`SimpleTaskHelper` возвращает `true`, когда с начала шага прошло `quota / 4` миллисекунд.

## Настройка quota и delay

Две ручки отвечают за разное, и путать их не стоит.

| Ручка | За что отвечает | Крутить ради |
|---|---|---|
| `quota` | Длину непрерывного блока | Отзывчивости |
| `delay` | Долю процессора, отданную наружу | Скорости счёта |

Реальная длина блока получается около `quota × 1.25`: бюджет проверяется уже после того, как шаг закончился, поэтому последний шаг всегда немного выходит за границу. Задаче при этом достаётся примерно `quota / (quota + delay)` процессорного времени.

| quota | delay | Блок | CPU | Когда |
|---|---|---|---|---|
| 300 | 50 | ~375 мс | 86% | Так делать не надо, это демонстрация проблемы |
| 16 | 8 | ~20 мс | 67% | Граница кадра, лёгкий джиттер |
| **8** | **4** | **~10 мс** | **67%** | Разумное значение по умолчанию, укладывается в кадр |
| 5 | 0 | ~6 мс | ~85% | Так стоит настраивать в реальном коде |
| 4 | 2 | ~5 мс | 67% | Бюджет React Fiber, максимально плавно |

`delay: 0` — не опечатка. Node зажимает его примерно до миллисекунды, и этого достаточно, чтобы отработали таймеры и I/O. Смысл не в том, чтобы простаивать, а в том, чтобы отдать управление. Опускаться ниже `quota: 4` уже бессмысленно: клэмпинг `setTimeout` (миллисекунда в Node, четыре для вложенных таймеров в браузере) начнёт съедать заметную часть такта.

Ориентиры под рукой: 16.6 мс — это один кадр при 60 FPS, 50 мс — порог «долгой задачи» в Core Web Vitals, около 5 мс — срез React Fiber.

Одна и та же работа, тот же heartbeat на 10 мс, менялись только настройки.

## Как это работает

### Цикл планировщика

```
push(job) → queueMicrotask(цикл)
              │
              ├─ снять задачу с начала очереди
              ├─ выполнить один шаг: job.next()
              ├─ не закончилась? отправить в конец            ← round robin
              ├─ вызвать handler(result)
              │
              ├─ бюджет не исчерпан? → крутим дальше синхронно
              └─ исчерпан?           → setTimeout(цикл, delay) ← настоящая уступка
```

Бюджет мягкий. Проверка происходит после того, как шаг вернул управление, поэтому шаг, ни разу не вызвавший `shouldPause()`, будет держать поток сколько захочет, а планировщик узнает об этом задним числом. Это свойство самой кооперативной модели, а не изъян реализации, — именно из-за него в Go 1.14 пришлось добавить асинхронное вытеснение горутин.

### Почему `queueMicrotask` не точка уступки

Микрозадачи разгребаются полностью до того, как event loop двинется дальше: раньше отрисовки и раньше следующей макрозадачи. Планируя продолжение микрозадачей, Вы всего лишь переставите порядок вызовов, но поток так и не отдадите:

```js
// Не уступает никогда. Страница мертва.
const loop = () => { work(); queueMicrotask(loop); };
```

Библиотека использует `queueMicrotask` ровно один раз — чтобы отложить старт цикла и дать вызывающему коду успеть повесить обработчики и начать итерацию до первых данных. Настоящая уступка всегда происходит через `setTimeout`.

В боевой версии точку выхода стоило бы сделать стратегией и выбирать по платформе: `MessageChannel` (макрозадача без клэмпинга), `setImmediate` (Node, срабатывает после I/O) или `scheduler.yield()` (свежий Chrome).

### Буфер в EventEmitter

Логика симметричная с обеих сторон:

- **Пришли данные.** Кто-то ждёт — отдаём ему. Никто не ждёт — кладём в буфер.
- **Вызвали `next()`.** В буфере что-то есть — отдаём сразу. Пусто — встаём в очередь ожидающих.

Отсюда три следствия, о которых стоит знать.

**Очередь резолверов, а не одно поле.** С одним общим промисом два параллельных `next()` получили бы один и тот же промис, а значит и одно и то же значение, — контракт асинхронного итератора нарушается напрямую.

**Внутренний сток отделён от публичных хранилищ.** Кормить буфер через `this.on("data", ...)` было бы ненадёжно: `off()` без аргументов делает `store.clear()` и снёс бы вместе с чужими обработчиками собственную подписку библиотеки. Поэтому `emit` сначала явно вызывает внутренний сток и только потом обходит публичные множества.

**Буферизация ленивая**, включается при первом обращении к `[Symbol.asyncIterator]()`. Если буферизовать с момента создания, то у того, кто пользуется только `.on("data")` и никогда не итерируется, буфер будет копиться всё время жизни задачи: мы просто поменяли бы потерю данных на утечку памяти. Обратная сторона: итерацию нужно начать до первого `await`. На практике `for await` ставится синхронно, а планировщик стартует через микрозадачу, так что это окно закрыто.

### Отмена

`scheduler.clear()` делает четыре вещи, и важна каждая:

1. **Снимает отложенный `setTimeout`.** Иначе `push()`, пришедший между `clear()` и срабатыванием таймера, вернёт `#running` в `true`, и старый таймер запустит второй цикл поверх той же очереди.
2. **Увеличивает счётчик поколений.** Отменить уже поставленный `queueMicrotask` нельзя, поэтому каждый цикл запоминает номер поколения на старте и тихо завершается, когда номер перестаёт совпадать. Гонка та же, примитив планирования другой.
3. **Закрывает генераторы через `job.return()`.** Именно это заставляет отработать блоки `finally` внутри пользовательских генераторов, чтобы ресурсы освободились.
4. **Сеттлит промисы всех живых задач** ошибкой `TaskCancelledError`. Без этого они висели бы вечно.

Очередь при этом чистится через `splice`, а не присваиванием нового массива: результат тот же, но уже выделенная ёмкость сохраняется и не набирается заново при следующих `push`.

### EventablePromise

Вместо наследования от `Promise` библиотека просто определяет свойства на обычном промисе. `then`, `catch` и `finally` переопределены так, чтобы рекурсивно применять декорацию к производному промису, — благодаря этому `exec(n).catch(console.error)` остаётся итерируемым.

Две детали. Оригинальные методы берутся с `Promise.prototype`, а не с самого объекта, иначе можно поймать уже переопределённую версию. И все свойства объявлены как `configurable` и `writable`, чтобы форма объекта оставалась одинаковой на каждом шаге цепочки.

Промис реджектится значением `result.error`, а не обёрткой `{ done, error, value }`: так сохраняются стектрейс и `instanceof`. В `.on("error")` обёртка при этом приезжает целиком.

Ещё внутри на промис вешается молчаливый `catch(() => {})`. Без него ловля ошибок только через `.on("error")` оставляла бы необработанный реджект, а начиная с Node 15 это по умолчанию роняет процесс. Обратная сторона: если не повесить ни `.catch`, ни `on("error")`, ошибка потеряется без следа.

## Демо

| Команда | Что смотреть в выводе |
|---|---|
| `npm run demo:problem` | Heartbeat молчит секундами |
| `npm run demo:cooperative` | Heartbeat держится в пределах 10–20 мс, работают все три интерфейса |
| `npm run demo:parallel` | Чередование A/B; от добавления задач простой не растёт |
| `npm run demo:cancel` | Печатается строка из `finally`, ошибка приходит со стеком, процесс завершается сам |
| `npm run demo:error` | Оба пути ошибки; процесс переживает падение, не пойманное промисом |

Две вещи в выводе стоит объяснить отдельно.

**Четыре строки `on(data)` подряд.** Шаг длится `quota / 4`, а бюджет проверяется после шага: 2, 4, 6, 8 мс — и на восьми такт заканчивается.

**Чанки растут с ~3 500 до ~41 000.** Окно всё время одно и то же, 2 мс, а работы в него влезает в двенадцать раз больше. Это прогрев JIT: первые чанки считает интерпретатор, потом функция становится горячей и уходит в оптимизирующий компилятор.

Отсюда практический вывод: бюджет нужно мерить в миллисекундах и никогда — в итерациях. `shouldPause()`, срабатывающий каждые 10 000 элементов, дал бы простой в 6 мс на холодном коде и 0.5 мс на прогретом. Порог один, а фриз отличается на порядок.

## Известные ограничения

Оставлены намеренно и на виду: репозиторий учебный.

**Рекурсия вместо цикла.** `run()` вызывает сам себя и наращивает стек. При большой `quota` и очень коротких шагах можно доехать до `RangeError: Maximum call stack size exceeded`. В боевом коде нужен `while`.

**`handler` вызывается внутри `try`.** Если пользовательский обработчик бросит исключение, сработает `catch` и `handler` будет вызван второй раз, уже с ошибкой.

**`#done` никогда не становится `true`.** Поле читается в `next()`, но нигде не пишется. На нормальном пути это безвредно: `for await` завершается по `{ done: true }` из буфера и больше `next()` не зовёт. А вот явный `next()` после завершения задачи повиснет навсегда.

**`any` слева от `extends` в `TaskBuilder`.** Условный тип с `any` слева разворачивается в объединение обеих веток, поэтому `infer D` и `infer R` не выводятся, и типы чанков схлопываются в `unknown`. В демо это обходится кастами, а чинится заменой на `F extends ...`.

**Нет бэкпрешера.** Буфер эмиттера растёт неограниченно, если потребитель медленнее производителя. На практике выручает устройство планировщика: потребитель разбирает буфер во время паузы `delay`, поэтому там лежит порядка `quota / шаг` элементов.

**Нет отмены отдельной задачи.** Есть только `scheduler.clear()`, который отменяет всё разом. Настоящий API принимал бы `AbortSignal` или возвращал хендл — вместо бесполезной длины очереди, которую сейчас отдаёт `push`.

**Нет приоритетов.** Round robin абсолютно справедлив, а это не всегда правильно: реакция на ввод должна вытеснять фоновый пересчёт.

**Нет `return()` у асинхронного итератора.** Если выйти из `for await` через `break`, ожидающие резолверы останутся неубранными.

**Сам замер не бесплатен.** `shouldPause()` дёргает `performance.now()` на каждой итерации Вашего цикла — при `n = 2_000_000` это четыре миллиона вызовов. На коротких шагах доля замера в шаге становится заметной. Лечится счётчиком, который сверяется с часами раз в 1024 итерации.

**Массив в роли дека.** `shift()` работает за O(n). Правильнее был бы кольцевой буфер.

**Тестов нет.** Минимальный набор выглядел бы так: чанки не теряются, стек не переполняется, `clear()` сеттлит промисы, ошибка доходит до обоих интерфейсов, две задачи чередуются.

## Где применять, а где не надо

**Хорошо подходит.** Фильтрация, сортировка и построение индексов по сотням тысяч строк, которые уже лежат в памяти. Постепенная отрисовка виртуализованного списка. Инкрементальная работа с текстом: подсветка синтаксиса, разбор markdown, построение diff. Обход больших деревьев и графов — там `yield*` позволяет писать рекурсивный обход как обычно, тогда как ручной конечный автомат потребовал бы явного стека. И вообще всё, чему нужны замыкания, кеши или DOM, где перенос данных в воркер обойдётся дороже самих вычислений.

**Плохо подходит.** Атомарные операции, которые нельзя разрезать: `JSON.parse`, `structuredClone`, регулярка с катастрофическим бэктрекингом. Чужой синхронный код, который Вы не собираетесь переписывать. Батчевая обработка, где важна пропускная способность и никто не ждёт освобождения потока. Тяжёлые вычисления на сервере под нагрузкой — там воркер-пул даст настоящий параллелизм по ядрам вместо деления одного ядра на всех.

**Лучше всего — вместе.** Самый сильный вариант: воркер, который внутри написан кооперативно. Тогда он остаётся отзывчивым к сообщениям и может крутить несколько задач по кругу. Эта библиотека работает внутри воркера без единой правки.

Отдельно про большой JSON: кооперативность здесь почти не помогает, потому что `JSON.parse` атомарен и приостановить его нельзя. Правильный ответ — потоковый парсер (`stream-json`, `clarinet`, `oboe`) либо разбор в воркере. Кооперативность нужна для обработки уже разобранных данных.
