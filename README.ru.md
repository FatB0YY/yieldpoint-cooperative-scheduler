# yieldpoint-cooperative-scheduler

Кооперативная многозадачность в TypeScript с нуля. Задачи-генераторы сами помечают точки уступки, сменный round-robin планировщик решает, когда действительно их прервать, и делит один бюджет времени на все задачи. Результат — промис, который можно ещё и итерировать или слушать.

Ноль зависимостей, около 600 строк, пять запускаемых демо. Написано, чтобы читать, а не подключать: это та же механика, что стоит за планировщиком React и за `scheduler.yield()`, но размером, который помещается в голову.

## Проблема

JavaScript исполняет код в одном потоке. Пока выполняется синхронная функция, движок не может ничего: ни отрисовать кадр, ни обработать клик, ни принять соединение, ни запустить колбэк таймера. Event loop крутится между задачами, а не внутри них.

```js
function bigArray(n) {
  const array = [];
  for (let i = 0; i < n; i++) array.push(i);
  return array;
}

for (let i = 0; i < 20; i++) {
  console.log(bigArray(1_000_000).length);
}
```

Запусти `node demo-problem.ts` и смотри на heartbeat. Таймер стоит на 10 мс и печатает реальный интервал между тиками:

```
heartbeat +10ms
heartbeat +10ms
--- начали считать ---
chunk: 1000000
...
heartbeat +2841ms
```

Почти три секунды тишины. В браузере это 170 пропущенных кадров. На сервере — 170 запросов, стоящих в очереди на приём.

Эффект накапливается. Один обработчик на 30 мс незаметен; сотня таких, пришедших одновременно, выстраивается в очередь, и последний запрос ждёт три секунды, чтобы обработаться за те же 30 мс. Хвостовые задержки взлетают задолго до того, как сдвинется среднее, поэтому мониторинг по среднему этого не покажет.

**Что мы на самом деле чиним:** не общий объём вычислений, а длину самого длинного непрерывного блока. Работы меньше не станет. Она станет нарезанной.

## Идея

Кооперативная многозадачность означает, что задача сама решает, когда отойти в сторону. Заставить её нельзя. Это противоположность вытесняющей модели, по которой работает твоя ОС: там планировщик отбирает процессор по прерыванию таймера, не спрашивая задачу.

Модель старая (Windows 3.x, Mac OS 9) и на уровне ОС от неё отказались не зря: одна недобросовестная программа вешала машину. Но она вернулась внутрь процессов, потому что там она дешёвая и не даёт гонок. Каждый `await` в JavaScript — кооперативная точка уступки. Как и горутины в Go, корутины в Kotlin, рабочий цикл React Fiber.

Механизм дают генераторы. Генератор запоминает, где остановился и что лежало в локальных переменных, поэтому обычный цикл можно приостанавливать и возобновлять, не выворачивая его наизнанку в конечный автомат:

```ts
function* work(t: TaskHelper, n: number) {
  let data: number[] = [];

  for (let i = 0; i < n; i++) {
    data.push(i);

    if (t.shouldPause()) {
      yield data; // здесь приостановились
      data = []; // сюда вернулись
    }
  }

  return "done";
}
```

**Место, на котором спотыкаются все:** `yield` сам по себе не отдаёт поток. Он возвращает управление тому, кто вызвал `.next()`, синхронно, в том же тике. Прогони генератор циклом `while` — и поток заблокирован ровно как раньше, плюс накладные расходы.

Управление доходит до event loop только потому, что раннер планирует следующий `.next()` через макрозадачу. Отсюда чёткое разделение обязанностей:

| Кто         | Что решает                                  |
| ----------- | ------------------------------------------- |
| Генератор   | Где его _можно_ прервать                    |
| Планировщик | Где его _действительно_ прервут и насколько |

На этом разделении построена вся библиотека.

## Использование

```ts
import { RoundRobinScheduler } from "./scheduler.ts";
import { taskBuilder, SimpleTaskHelper } from "./task.ts";

const scheduler = new RoundRobinScheduler({ quota: 8, delay: 4 });
const task = taskBuilder(scheduler)(SimpleTaskHelper);

const exec = task(function* doSomething(t, n: number) {
  let data: number[] = [];

  for (let i = 0; i < n; i++) {
    data.push(i);

    if (t.shouldPause()) {
      yield data;
      data = [];
    }
  }

  if (data.length > 0) yield data;

  return "done";
});

const run = exec(2_000_000);
```

Создание каррировано в три уровня, чтобы настроить один раз и вызывать много:

```
taskBuilder(scheduler)   // 1. какой планировщик  ─┐ один раз
           (Helper)      // 2. какой хелпер       ─┘ на приложение
           (generator)   // 3. какая функция      ─── на каждую задачу
```

Первый аргумент генератора — всегда хелпер, его подставляет библиотека. Твои собственные аргументы начинаются со второго, и возвращённая функция принимает только их.

### Три способа получить результат

`exec()` возвращает один объект, который удовлетворяет трём интерфейсам сразу. Пользуйся тем, что удобнее.

```ts
const run = exec(2_000_000);

run.on("data", (r) => {
  if (!r.done) console.log("чанк", r.value.length);
});

for await (const chunk of run) {
  console.log("чанк", chunk.length);
}

const result = await run; // "done"
```

События срабатывают синхронно, внутри занятого блока. Асинхронная итерация просыпается на микрозадачах, то есть после конца синхронного блока. Поэтому в выводе сначала идёт пачка строк `on(data)`, а следом та же пачка `for await`. Это правильный порядок, а не баг.

Цепочка переживает `.then`, `.catch` и `.finally`, так что это работает:

```ts
for await (const chunk of exec(n).catch(console.error)) { ... }
```

### `event-emitter.ts`

Раздаёт два события, `data` и `error`, и одновременно работает как асинхронный итерируемый объект. Оба интерфейса живут на одном объекте.

Самое интересное здесь — буфер. Планировщик успевает сделать несколько шагов задачи внутри одного синхронного блока и несколько раз вызвать `emit()`, а потребитель асинхронной итерации просыпается только на микрозадаче, то есть после конца блока. Наивная реализация с ленивой подпиской внутри `next()` из-за этого теряет все чанки, кроме первого. Эмиттер держит буфер непрочитанного и FIFO-очередь ожидающих резолверов, поэтому ничего не теряется, а два параллельных `next()` получают разные значения.

Экспортирует `EventEmitter`, `TEvent`, `TDataResult`, `TErrorResult`, `TDataHandler`, `TErrorHandler`.

### `scheduler.ts`

Решает, какая задача считается сейчас, сколько всего можно держать поток и когда спать. Алгоритм — round robin: каждая задача получает один шаг и уезжает в конец очереди.

Планировщик — стратегия. Реализуй `IScheduler` сам (очередь с приоритетами, что-то вроде lanes в React) и передай в `taskBuilder`, не трогая остальное.

Интерфейс называется `IScheduler`, а не `Scheduler`, потому что глобальный `Scheduler` уже занят DOM lib (Prioritized Task Scheduling API). Назови свой так же — и TypeScript начнёт требовать реализацию чужих `postTask` и `yield`.

Экспортирует `RoundRobinScheduler`, `IScheduler`, `ISchedulerOptions`, `IJobResult`, `TaskCancelledError`.

### `task.ts`

Оборачивает генератор, регистрирует его в планировщике и связывает каждый шаг с промисом и эмиттером.

Здесь же живёт `TaskHelper` — вторая стратегия библиотеки. Хелпер решает, когда генератору стоит предложить паузу. `SimpleTaskHelper` делает это по часам; можно написать хелпер, который смотрит на `navigator.scheduling.isInputPending()`, или адаптирует порог, или учитывает приоритеты.

Экспортирует `taskBuilder`, `SimpleTaskHelper`, `TaskHelper`, `TaskHelperConstructor`, `TaskBuilder`, `EventablePromise`.

## API

### `new RoundRobinScheduler({ quota, delay })`

| Опция   | Смысл                                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `quota` | Сколько миллисекунд можно держать поток за один такт — **на все задачи вместе**. Это максимальная задержка, которую ты навязываешь всему остальному в потоке. |
| `delay` | Сколько миллисекунд спать между тактами. Управляет долей CPU, а не отзывчивостью.                                                                             |

| Член                 | Описание                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `quota`, `delay`     | Геттеры только на чтение                                                                             |
| `isRunning()`        | Крутится ли цикл прямо сейчас                                                                        |
| `push(job, handler)` | Зарегистрировать итератор; `handler` вызывается с результатом каждого шага. Возвращает длину очереди |
| `run()`              | Запустить цикл. Идемпотентно, `push` вызывает сам                                                    |
| `clear()`            | Отменить всё: закрыть генераторы, сеттлить промисы, снять отложенный таймер                          |

### `taskBuilder(scheduler)(Helper)(generator)`

Возвращает функцию, которая принимает аргументы твоего генератора без ведущего хелпера и возвращает `EventablePromise`.

### `EventablePromise`

| Член                            | Описание                                                          |
| ------------------------------- | ----------------------------------------------------------------- |
| `await`                         | Значение из `return` генератора                                   |
| `.on("data", h)`                | Каждый шаг в виде `{ done, value }`. Возвращает себя для чейнинга |
| `.on("error", h)`               | `{ done: true, error, value: undefined }`. Возвращает себя        |
| `.off(event?, handler?)`        | Снять один обработчик, все обработчики события или вообще всё     |
| `for await`                     | Отдаёт промежуточные значения, завершается на финальном шаге      |
| `.then` / `.catch` / `.finally` | Стандартное поведение, результат остаётся eventable               |

### `TaskHelper`

```ts
interface TaskHelper {
  shouldPause(): boolean;
}
```

`SimpleTaskHelper` возвращает `true`, когда с начала шага прошло `quota / 4` миллисекунд.

## Настройка quota и delay

Две ручки делают разное, и их легко перепутать.

| Ручка   | За что отвечает           | Крутить ради   |
| ------- | ------------------------- | -------------- |
| `quota` | Длина непрерывного блока  | Отзывчивости   |
| `delay` | Доля CPU, отданная наружу | Скорости счёта |

Реальная длина блока ≈ `quota × 1.25`, потому что бюджет проверяется _после_ завершения шага, и последний шаг всегда выходит за границу. Доля CPU у задачи ≈ `quota / (quota + delay)`.

| quota | delay | Блок       | CPU     | Когда                                  |
| ----- | ----- | ---------- | ------- | -------------------------------------- |
| 300   | 50    | ~375 мс    | 86%     | Никогда. Это картинка «до»             |
| 16    | 8     | ~20 мс     | 67%     | Граница кадра, лёгкий джиттер          |
| **8** | **4** | **~10 мс** | **67%** | Хороший дефолт, влезает в кадр         |
| 5     | 0     | ~6 мс      | ~85%    | Как настроил бы в бою                  |
| 4     | 2     | ~5 мс      | 67%     | Бюджет React Fiber, максимально плавно |

`delay: 0` — не опечатка. Node зажимает его примерно до 1 мс, и этого хватает, чтобы отработали таймеры и I/O. Смысл в том, чтобы _отдать_ управление, а не простаивать. Ниже `quota: 4` спускаться не стоит: клэмпинг `setTimeout` (1 мс в Node, 4 мс для вложенных таймеров в браузере) начинает съедать заметную долю такта.

Ориентиры: 16.6 мс — кадр при 60 FPS, 50 мс — порог «долгой задачи» в Core Web Vitals, 5 мс — примерный срез React Fiber.

## Как это работает

### Цикл планировщика

```
push(job) → queueMicrotask(цикл)
              │
              ├─ снять задачу с начала очереди
              ├─ выполнить один шаг: job.next()
              ├─ не закончилась? отправить в конец            ← round robin
              ├─ вызвать handler(result)
              │
              ├─ бюджет не исчерпан? → крутим дальше синхронно
              └─ исчерпан?           → setTimeout(цикл, delay) ← настоящая уступка
```

Бюджет мягкий. Проверка идёт после возврата из шага, поэтому шаг, который вообще не вызывает `shouldPause()`, будет держать поток сколько захочет, а планировщик узнает об этом задним числом. Это свойство самой кооперативной модели, а не изъян реализации. Ровно поэтому в Go 1.14 добавили асинхронное вытеснение.

### Почему `queueMicrotask` не точка уступки

Микрозадачи дренируются полностью до того, как event loop пойдёт дальше — раньше рендеринга и раньше следующей макрозадачи. Планировать продолжение микрозадачей значит переставить порядок вызовов, ни разу не отдав поток:

```js
// Не уступает никогда. Страница мертва.
const loop = () => {
  work();
  queueMicrotask(loop);
};
```

Библиотека использует `queueMicrotask` ровно один раз — чтобы отложить _старт_ цикла и дать вызывающему коду повесить обработчики и начать итерацию до первых данных. Настоящая уступка — всегда `setTimeout`.

В продакшене точку выхода стоило бы сделать стратегией и подставлять по платформе `MessageChannel` (макрозадача без клэмпинга), `setImmediate` (Node, выполняется после I/O) или `scheduler.yield()` (новый Chrome).

### Буфер в EventEmitter

Логика симметричная с обеих сторон:

- **Пришли данные.** Кто-то ждёт? Отдаём ему. Никто? Кладём в буфер.
- **Вызвали `next()`.** Есть в буфере? Отдаём сразу. Нет? Становимся в очередь ожидающих.

Три следствия, о которых стоит знать:

**Очередь резолверов, а не одно поле.** С одним общим промисом два параллельных `next()` получили бы один и тот же промис, а значит одно и то же значение, — прямое нарушение контракта асинхронного итератора.

**Внутренний сток отделён от публичных хранилищ.** Кормить буфер через `this.on("data", ...)` было бы хрупко: пользователь, вызвавший `off()` без аргументов, делает `store.clear()` и снёс бы собственную подписку библиотеки. Поэтому `emit` сначала явно вызывает внутренний сток и только потом обходит публичные множества.

**Буферизация ленивая.** Включается на первом вызове `[Symbol.asyncIterator]()`. Буферизовать с момента создания значило бы, что потребитель, использующий только `.on("data")` и никогда не итерирующийся, накапливает все чанки на всё время жизни задачи, — мы бы поменяли потерю данных на утечку памяти. Плата за ленивость: итерацию надо начать до первого `await`. На практике `for await` ставится синхронно, а планировщик стартует через микрозадачу, так что окно закрыто.

### Отмена

`scheduler.clear()` делает четыре вещи, и важны все четыре:

1. **Снимает отложенный `setTimeout`.** Иначе `push()`, пришедший между `clear()` и срабатыванием таймера, вернёт `#running` в `true`, и старый таймер запустит _второй_ цикл по той же очереди.
2. **Инкрементит счётчик поколений.** Отменить поставленный `queueMicrotask` нельзя, поэтому каждый цикл запоминает поколение на старте и тихо умирает, когда оно перестаёт совпадать. Та же гонка, другой примитив планирования.
3. **Закрывает генераторы через `job.return()`.** Именно это заставляет отработать блоки `finally` внутри пользовательских генераторов, чтобы ресурсы освободились.
4. **Сеттлит промисы всех живых задач** с `TaskCancelledError`. Без этого они висели бы вечно.

Заметь, что очередь чистится через `splice`, а не присваиванием нового массива. Результат тот же, но уже выделенная ёмкость сохраняется, вместо того чтобы набираться заново при следующих `push`.

### EventablePromise

Вместо наследования от `Promise` библиотека определяет свойства на обычном промисе. `then`, `catch` и `finally` переопределены так, чтобы рекурсивно применять декорацию к производному промису, — именно это оставляет `exec(n).catch(console.error)` итерируемым.

Две детали: оригиналы берутся с `Promise.prototype`, а не с объекта, поэтому уже переопределённый метод никогда не попадётся; и все свойства объявлены как `configurable` и `writable`, чтобы форма оставалась согласованной.

Ошибки реджектятся значением `result.error`, а не обёрткой `{ done, error, value }`, — так выживают стектрейсы и `instanceof`. В `.on("error")` обёртка при этом доезжает целиком.

Ещё библиотека внутри вешает молчаливый `promise.catch(() => {})`. Без него обработка ошибок только через `.on("error")` оставляла бы необработанный реджект, а это в Node 15+ по умолчанию роняет процесс. Плата: не повесив ни `.catch`, ни `on("error")`, ошибку можно потерять молча.

## Демо

| Команда                    | На что смотреть                                                       |
| -------------------------- | --------------------------------------------------------------------- |
| `npm run demo:problem`     | Heartbeat молчит секундами                                            |
| `npm run demo:cooperative` | Heartbeat держится в ~10–20 мс; все три интерфейса                    |
| `npm run demo:parallel`    | Чередование A/B; добавление задач не удлиняет простой                 |
| `npm run demo:cancel`      | Печатается строка из `finally`, ошибка со стеком, процесс завершается |
| `npm run demo:error`       | Оба пути ошибки; процесс переживает падение, не пойманное промисом    |

Две вещи в выводе стоит понимать.

**Четыре строки `on(data)` подряд.** Шаг длится `quota / 4`, бюджет проверяется после: 2, 4, 6, 8 мс, и на восьми такт заканчивается.

**Чанки растут с ~3 500 до ~41 000.** Окно постоянное, 2 мс, а работы в него влезает в двенадцать раз больше. Это прогрев JIT: первые чанки исполняются интерпретатором, потом функция становится горячей и уходит в оптимизирующий компилятор.

Практический вывод: **бюджет мерить в миллисекундах, никогда в итерациях.** `shouldPause()`, срабатывающий каждые 10 000 элементов, дал бы простой в 6 мс на холодную и 0.5 мс на горячую. Один порог, совершенно разный фриз.

## Известные ограничения

Оставлены намеренно и на виду. Это учебный репозиторий.

**Рекурсия вместо цикла.** `run()` вызывает себя, наращивая стек. При большой `quota` и очень коротких шагах можно доехать до `RangeError: Maximum call stack size exceeded`. В боевом коде нужен `while`.

**`handler` вызывается внутри `try`.** Если пользовательский обработчик бросит исключение, сработает `catch` и `handler` будет вызван второй раз, уже с ошибкой.

**`#done` никогда не выставляется в `true`.** Поле читается в `next()`, но не пишется. На нормальном пути безвредно: `for await` завершается по `{ done: true }` из буфера и больше не зовёт `next()`. Явный `next()` после завершения повиснет.

**`any` слева от `extends` в `TaskBuilder`.** Условный тип с `any` слева разворачивается в объединение обеих веток, поэтому `infer D` и `infer R` не выводятся, и типы чанков схлопываются в `unknown`. Демо обходят это кастами. Правильно — `F extends ...`.

**Нет бэкпрешера.** Буфер эмиттера растёт неограниченно, если потребитель медленнее производителя. На практике спасает планировщик: потребитель дренирует буфер во время паузы `delay`, поэтому в буфере лежит порядка `quota / шаг` элементов.

**Нет отмены отдельной задачи.** Только `scheduler.clear()`, который отменяет всё. Настоящий API принимал бы `AbortSignal` или возвращал хендл вместо бесполезной длины очереди из `push`.

**Нет приоритетов.** Round robin абсолютно справедлив, что не всегда правильно: реакция на ввод должна вытеснять фоновый пересчёт.

**Нет `return()` у асинхронного итератора.** При `break` из `for await` ожидающие резолверы не чистятся.

**Замер сам по себе стоит денег.** `shouldPause()` вызывает `performance.now()` на каждой итерации твоего цикла — четыре миллиона вызовов при `n = 2_000_000`. На коротких шагах это заметная доля шага. Лечится счётчиком, который сверяется с часами раз в 1024 итерации.

**Массив в роли дека.** `shift()` — O(n). Правильно был бы кольцевой буфер.

**Тестов нет.** Минимальный набор: чанки не теряются, стек не переполняется, `clear()` сеттлит промисы, ошибка доходит до обоих интерфейсов, две задачи чередуются.

## Где применять, а где не надо

**Хорошо подходит.** Фильтрация, сортировка и построение индексов по сотням тысяч строк, которые уже в памяти. Постепенный рендер виртуализованного списка. Инкрементальная работа с текстом: подсветка синтаксиса, разбор markdown, diff. Обход больших деревьев и графов, где `yield*` делает рекурсивный обход естественным, а ручной конечный автомат потребовал бы явного стека. Всё, чему нужны замыкания, кеши или DOM, где перенос данных в воркер дороже самих вычислений.

**Плохо подходит.** Атомарные операции, которые нельзя разрезать: `JSON.parse`, `structuredClone`, регулярка с катастрофическим бэктрекингом. Чужой синхронный код, который ты не будешь переписывать. Батчевая работа, где важна пропускная способность и никто не ждёт поток. Тяжёлые вычисления на сервере под нагрузкой, где воркер-пул даёт настоящий параллелизм по ядрам вместо деления одного ядра.

**Комбинируй.** Самый сильный вариант — воркер, который сам написан кооперативно: он остаётся отзывчивым к сообщениям и может крутить несколько задач по кругу. Эта библиотека работает внутри воркера без изменений.

Про большой JSON отдельно: кооперативность здесь помогает слабо, `JSON.parse` атомарен и приостановить его нельзя. Нужен потоковый парсер (`stream-json`, `clarinet`, `oboe`) либо разбор в воркере. Кооперативность — для _обработки_ уже разобранных данных.
